W1 (high, product bug): tests/unit/decoder-killnow.test.ts "kills a running ffmpeg synchronously..." timed out at 30 s.
  Cause (architect-opus diagnosis, confirm it): CI installs FFmpeg with Chocolatey, whose `ffmpeg.exe` on PATH is a SHIM that starts the
  real ffmpeg as a child. `child.kill('SIGKILL')` kills only the shim. The real ffmpeg keeps running and keeps the stdout pipe open, so
  onEnd never fires and the process leaks. Scoop also uses shims. Real users hit this.
  Fix in src/ingest/decoder.ts AND src/ingest/probe.ts (timeout kill) via one shared helper, e.g. src/ingest/kill-tree.ts:
  - killTreeSync(pid) / killTree(pid): on win32 run `taskkill /pid <pid> /T /F` (spawnSync / spawn, argv array, windowsHide, no shell,
    ignore its output and exit code); elsewhere child.kill('SIGKILL') / 'SIGTERM' as now.
  - killNow() and stop() also destroy the child's stdout so onEnd can fire even if a descendant holds the pipe.
  - On win32, onEnd's `signal` may be null with a non-zero code after taskkill; tests must accept either (signal SIGKILL) or (code !== 0).
  Add a test that would have caught this on any OS: spawn the decoder through a tiny shim (a node script in tests/helpers that spawns
  ffmpeg with the same argv, pipes its stdout through, and does NOT forward signals) as ffmpegPath; killNow() must still end the real
  ffmpeg (on Unix the shim test may use process groups: if you cannot make the Unix path kill grandchildren without process groups,
  spawn ffmpeg with `detached: false` and kill the group via the shim pid only on win32; on Unix document why direct ffmpeg is the
  supported path and skip the shim test there). Prefer a design where the test runs on all three OSes.
